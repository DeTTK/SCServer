# Участие в разработке

Перед первым PR прочитайте `NOTICE.md`: лицензия пока не выбрана.
Сначала запустите `python scripts/build.py test` и посмотрите `docs/STATUS.md`.

1. Создайте Issue с конкретным воспроизведением или предложением.
2. Работайте в отдельной ветке `fix/...` или `feature/...`.
3. Сохраняйте изменения в исходниках и сборочных рецептах. Ручная замена единственной копии `.class` не считается воспроизводимым изменением.
4. Выполните аудит и подходящие тесты. В PR укажите проверенное поведение и ограничения.
5. Для игрового изменения добавьте версию/хеш частной базы и короткую запись воспроизведения, на которую есть право публикации.

## Технические правила

- Игровые обфусцированные имена держите в adapters/bridge. Серверным сервисам отдавайте обычные Java-типы.
- Reflection выбирает метод по имени, аргументам, возвращаемому типу и static/instance. Одного `getMethod(name)` недостаточно.
- IO, загрузка чанков и тяжёлые фабрики выполняются вне сетевого event loop и игрового owner-потока.
- Физика FPV принадлежит клиенту пилота. Сервер ведёт жизненный цикл, ретрансляцию и подписки на чанки.
- Формат карты и сетевые схемы изменяются с версией и миграцией. Старые числовые ID не переносятся автоматически.
- При переносе частной базы сохраняйте закреплённые реализации accessory physics `1262384494`, `212440292`, `108847398`, `1536296909`; замена требует отдельной проверки. Legacy decoded-классы не накладываются поверх promoted runtime автоматически.
- Сервер останавливается штатным сохранением. Не тестируйте разрушительные сценарии на пользовательских сохранениях.
- Автоматизированный графический тест допускается только со скрытым окном, отключённым звуком и проверенной блокировкой всех способов физического ввода, включая Raw Input.
- Игровой smoke-test и синтетический тест отмечаются отдельно. Компиляция не доказывает прохождение входа или сетевой сессии.

В PR не добавляются DLL, дампы игры, архивы целиком, токены, пользовательские карты и сырые логи с идентификаторами.
