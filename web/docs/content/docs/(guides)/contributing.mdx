# Как внести вклад

Вклад — это не только код. Полезны точные баг-репорты, исправления документации,
тесты, переводы и примеры модов. Ниже — безопасный путь для первого изменения.

<Callout title="Лицензия">
  Файла `LICENSE` в проекте пока нет: лицензия не выбрана. Перед первым крупным
  PR прочитайте `NOTICE.md` и не переносите чужой код без разрешения.
</Callout>

## 1. Подготовьте аккаунт и окружение

Вам понадобятся аккаунт GitHub, Git, Python 3.10+ и JDK 17. Команды выполняются из
корня проекта.

```sh
git clone https://github.com/<ваш-логин>/SCServer.git
cd SCServer
git remote add upstream https://github.com/oarer/SCServer.git
```

Если репозиторий ещё не форкнут, сначала нажмите **Fork** на GitHub. Работать
удобнее в своём форке, а изменения предлагать через Pull Request.

Проверьте, что база собирается до ваших правок:

```sh
python scripts/audit_public.py
python -m unittest discover -s scripts/tests
python scripts/build.py test
```

`build.py test` может занять несколько минут. Результат — `build/verification.json`.

## 2. Найдите задачу

- Посмотрите открытые Issue.
- Для нового бага сначала создайте Issue: что делали, что ожидали, что получилось.
- Для большого изменения лучше сначала согласовать подход, а не писать сотни строк.

Хороший Issue содержит:

- версию или ветку;
- шаги воспроизведения;
- ожидаемый и фактический результат;
- очищенный лог или stack trace без токенов, логинов и путей пользователя;
- для игровых проблем — карту/мир и версию приватной базы, если это важно.

<Callout title="Секреты">
  Не прикладывайте токены, пароли, ключи, сертификаты, `Server/data`, чужие карты,
  сохранения, DLL/дампы и сырые логи с идентификаторами. Если сомневаетесь —
  пришлите фрагмент с заменёнными значениями.
</Callout>

## 3. Создайте ветку

Не работайте прямо в `main`.

```sh
git fetch upstream
git checkout -b fix/short-description upstream/main
```

Имя ветки: `fix/...` для исправления, `feature/...` для возможности,
`docs/...` для документации.

## 4. Внесите изменение

Меняйте исходники и сборочные рецепты так, чтобы результат воспроизводился.
Ручная замена `.class`, DLL или готового JAR не принимается.

| Что меняете | Куда смотреть |
| --- | --- |
| Сервер, сеть, мир, инвентарь | `server/src/main/java/` |
| Моды и API | `sdk/`, `client/mod-runtime/`, `docs/SDK.md` |
| Лаунчер | `launcher/` |
| Сборка и проверки | `scripts/`, `.github/workflows/` |
| Документация | `docs/` и этот сайт в `web/docs/content/docs/` |

Технические правила проекта коротко:

- обфусцированные игровые имена остаются в adapters/bridge;
- reflection ищет метод по имени, аргументам, возвращаемому типу и
  `static`/`instance`;
- тяжёлые операции не выполняются в сетевом или игровом owner-потоке;
- форматы карты, сохранений и сети меняются только с версией и миграцией;
- публичный API модов меняется синхронно в `sdk/api/` и
  `client/mod-runtime/src/szmods/api/`.

Подробности — в `AGENTS.md` и `docs/ARCHITECTURE.md`.

## 5. Запустите проверки

Минимум для любого PR:

```sh
python scripts/audit_public.py
```

Дальше — по затронутым частям:

| Изменение | Команда |
| --- | --- |
| Сервер, SDK, общий код | `python scripts/build.py test` |
| Мод или пример | `python scripts/build.py sdk` |
| Подсказки команд | `python scripts/build.py command-completion` |
| Масштаб персонажа | `python client-compat/character-scale/build.py` |
| Лаунчер, Windows | `cargo test --manifest-path launcher/Cargo.toml --workspace --locked` |
| Только документация | `python scripts/audit_public.py` |

<Callout title="Тесты ≠ игра">
  Синтетические тесты не доказывают вход в мир, сетевую сессию или отрисовку.
  Игровой прогон отмечайте отдельно и честно пишите, что осталось непроверенным.
</Callout>

Если меняли внешний вид или игровое поведение, приложите короткое описание
ручной проверки. Для графических прогонов окно скрывается, звук отключается,
физический ввод блокируется.

## 6. Сделайте коммит и PR

```sh
git status
git diff
git add <файлы>
git commit -m "Коротко: что и зачем"
git push -u origin fix/short-description
```

Затем откройте Pull Request в `DeTTK/SCServer`. В описании заполните:

1. **Что это** — одно-два предложения.
2. **Воспроизведение** — было/стало, затронутые компоненты.
3. **Проверка** — какие команды запускали и что получили.
4. **Игровой прогон** — если был, с деталями; если нет — так и напишите.
5. **Миграция и откат** — если меняются данные или форматы.
6. **Совместимость** — API модов, имена, закреплённые реализации.

Не удаляйте пустые пункты шаблона: пометка «не проверял» полезнее, чем пропуск.

## 7. Что не попадёт в PR

- токены, ключи, сертификаты, `.env` с секретами;
- `Server/data`, персонажи, журналы, checkpoint;
- игровые ассеты, карты, `classes.jar`, DLL, дампы;
- целые архивы и чужие сохранения;
- новые зависимости без закрепления SHA-256 в `dependencies.lock.json`;
- изменения, которые нельзя повторить из исходников.

## Если вы не программист

- Уточните шаг в документации, где вы застряли.
- Пришлите воспроизводимый баг с очищенным логом.
- Исправьте опечатку или неточную команду в `docs/` или на сайте.
- Предложите перевод или более понятную формулировку.
- Добавьте пример использования мода, если он не раскрывает API.

Начните с одного небольшого изменения — так проще пройти ревью и понять процесс.
