# BSCPCRAFT · Rust + Slint · launtest

Нативный Windows x64 лаунчер и отдельный Rust Supervisor. .NET и WebView не требуются. Пользователь выбирает ветку проекта, адреса загрузок и публичный ключ встроены в программу.

Supervisor запускается по необходимости для запуска/управления клиентом, сервером или применения обновления. В простое интерфейс не создаёт фоновый процесс; проверка уже установленной сборки обходится без него. После завершения процессов и операций supervisor выходит через 5–8 секунд. Закрытие интерфейса при работающей игре или сервере оставляет управление и сбор журналов активными.

## Сборка

Нужны Rust stable с MSRV Slint 1.19, MSVC Build Tools и JDK 17 для bridge. `powershell -File build.ps1` собирает native-комплект в `dist`. `-OutputPath` выбирает другую папку. По умолчанию Java в него не копируется: она входит в полную игровую установку build-ветки. Для особой офлайн-поставки доступны `-IncludeJava -JavaRoot <jlink-runtime>` и `-BridgeJar <bridge.jar>`.

## Первый запуск

Запустите `BSCPCRAFT.exe`, выберите установленный STALCRAFT с ресурсами, папку данных и ник. Затем выберите ветку `launtest` и нажмите «Установить игру». Лаунчер получает из `build-launtest` полную проверенную основу: Java, runtime клиента и сервера, нативные библиотеки, bridge и базовую карту. Старый комплект и архивы игровых Releases для этого не нужны. На последнем шаге создаётся первый мир и подключаются актуальные файлы ветки.

Нужные оригинальные игровые ассеты берутся из установленной игры и остаются на месте. Ветка build содержит весь дополнительный комплект локалки, а не оригинальные ассеты установленного STALCRAFT.

Поле распакованного комплекта в мастере отсутствует: папка основы определяется автоматически. Перед загрузкой проверяются имеющиеся файлы, кэш и незавершённые части. Прогресс показывает общий объём игровых данных, полученных из сети за операцию, оставшиеся байты, скорость за последние пять секунд и примерное время скачивания. Байты из кэша не считаются сетевым трафиком. HTTP-заголовки, TLS и маленькие служебные запросы описаний сборки в этот счётчик не входят. Сборка и проверка файлов показываются отдельными этапами.

## Как доставляются файлы

Встроенный адрес — `DeTTK/SCServer`. Исходная ветка `launtest` соответствует готовой `build-launtest`. Лаунчер фиксирует commit, проверяет RSA-подпись `delivery.json`, SHA-256 индексов, объектов и готовых файлов. Маленькие файлы основы сгруппированы в небольшие объекты; одинаковые байты используются повторно. Обновляемые JAR скачиваются отдельно. При повторной установке совпадающие объекты и версии берутся из кэша.

Основа размещается в `GameData/bundles/foundation-*`, новые компоненты — в `GameData/channels/<channel-id>/revisions`. Изменённые файлы имеют приоритет над неизменяемой основой; полная копия основы для каждого обновления не создаётся. Применение обновления требует остановленной игры и сервера. Неудачная загрузка не меняет активный указатель. Предыдущая версия остаётся доступной для отката.

Настройки, локальная идентичность, состояние и журналы — рядом с EXE либо в указанном `--root <portable-root>`. Реестр/AppData не используются для настроек лаунчера. Клиентские профили разделены по веткам. Миры и их базовые карты хранятся отдельно; обновление клиента/сервера не подменяет карту существующего мира.

Подробности исходной публикации и сборок — в `delivery/README.md` репозитория. Поддержка старого подписанного release-feed и pinned ZIP сохранена только для совместимости и отката, в новом пользовательском потоке ссылки вводить не нужно.

## Диагностика и проверка

`cargo test --workspace -j 4` проверяет ядро, Supervisor и контроллер. Пример `channel_probe <root> launtest check|install|rollback` проверяет настоящий публичный канал без Git и токенов; команда `setup <installed-game>` подготавливает первый мир в явно указанном portable-root.

`BSCPCRAFT.exe --root <root> --rpc status|metrics` возвращает реальные данные процессов и JVM. Отчёт создаётся локально; включение JFR требует отдельного выбора. Отправка в сеть автоматически не выполняется.

Программный рендерер выбран по умолчанию. `--renderer femtovg` включает GPU. Для диагностического снимка настоящего интерфейса: `--capture <snapshot.ppm>`; окно размещается вне видимой области и закрывается после снимка, рабочий стол не управляется.
