Единый EXE (0.5.0): интерфейс запускается обычным образом; фоновый supervisor — тем же `BSCPCRAFT.exe --host --root <root>`. Отдельный `bscp-host.exe` не нужен. Фоновый режим не создаёт окно и не инициализирует Slint. Для диагностики доступен `--rpc`; при запуске из кода захватывайте stdout процесса.

# BSCPCRAFT · Rust + Slint

Нативный Windows x64 лаунчер и отдельный Rust Supervisor. .NET и WebView не требуются. Пользователь выбирает ветку проекта, адреса загрузок и публичный ключ встроены в программу.

Supervisor запускается по необходимости для запуска/управления клиентом, сервером или применения обновления. В простое интерфейс не создаёт фоновый процесс; проверка уже установленной сборки обходится без него. После завершения процессов и операций supervisor выходит через 5–8 секунд. Закрытие интерфейса при работающей игре или сервере оставляет управление и сбор журналов активными.

## Сборка

Нужны Rust stable с MSRV Slint 1.19, MSVC Build Tools и JDK 17 для bridge. `powershell -File build.ps1` собирает native-комплект в `dist`. `-OutputPath` выбирает другую папку. По умолчанию Java в него не копируется: она входит в полную игровую установку build-ветки. Для особой офлайн-поставки доступны `-IncludeJava -JavaRoot <jlink-runtime>` и `-BridgeJar <bridge.jar>`.

## Первый запуск

Оформление использует предоставленные проектом векторный логотип «Билдерс СК» и персонажа: единая чёрно-белая палитра, встроенная иконка Windows и графика без внешних файлов. На последнем шаге мастера можно отключить создание ярлыка на рабочем столе. Ярлык хранит путь к EXE, выбранный portable-root и иконку из самого EXE; уже настроенная установка не создаёт ярлык автоматически при обновлении.

Запустите `BSCPCRAFT.exe`, выберите установленный STALCRAFT с ресурсами, папку данных и ник. Затем выберите ветку `main` и нажмите «Установить игру». Лаунчер получает из `build-main` полную проверенную основу: Java, runtime клиента и сервера, нативные библиотеки, bridge и базовую карту. Старый комплект и архивы игровых Releases для этого не нужны. На последнем шаге создаётся первый мир и подключаются актуальные файлы ветки.

Нужные оригинальные игровые ассеты берутся из установленной игры и остаются на месте. Ветка build содержит весь дополнительный комплект локалки, а не оригинальные ассеты установленного STALCRAFT.

Поле распакованного комплекта в мастере отсутствует: папка основы определяется автоматически. Перед загрузкой проверяются имеющиеся файлы, кэш и незавершённые части. Прогресс показывает общий объём игровых данных, полученных из сети за операцию, оставшиеся байты, скорость за последние пять секунд и примерное время скачивания. Байты из кэша не считаются сетевым трафиком. HTTP-заголовки, TLS и маленькие служебные запросы описаний сборки в этот счётчик не входят. Сборка и проверка файлов показываются отдельными этапами.

## Как доставляются файлы

Встроенный адрес — `DeTTK/SCServer`. Исходная ветка `launtest` соответствует готовой `build-main`. Лаунчер фиксирует commit, проверяет RSA-подпись `delivery.json`, SHA-256 индексов, объектов и готовых файлов. Маленькие файлы основы сгруппированы в небольшие объекты; одинаковые байты используются повторно. Обновляемые JAR скачиваются отдельно. При повторной установке совпадающие объекты и версии берутся из кэша.

Основа размещается в `GameData/bundles/foundation-*`, новые компоненты — в `GameData/channels/<channel-id>/revisions`. Изменённые файлы имеют приоритет над неизменяемой основой; полная копия основы для каждого обновления не создаётся. Применение обновления требует остановленной игры и сервера. Неудачная загрузка не меняет активный указатель. Предыдущая версия остаётся доступной для отката.

Настройки, локальная идентичность, состояние и журналы — рядом с EXE либо в указанном `--root <portable-root>`. Реестр/AppData не используются для настроек лаунчера. Клиентские профили разделены по веткам.

Мир формата 2 — самостоятельная папка `GameData/worlds/<id>` с `Map`, `data`, `world.properties` и `world.json`. Скачанная карта используется только как шаблон новых миров. Копирование и экспорт включают всю карту и прогресс; импорт работает в пустой установке, восстановление заменяет карту и данные одной восстанавливаемой транзакцией. Изменяемые файлы миров не связаны hardlink с шаблоном или другими мирами. Обновление компонентов не заменяет карту существующего мира.

Старые миры формата 1 подготавливаются офлайн через `szserver.world.PortableWorld migrate` перед запуском, копированием или экспортом. Исходные данные и внешняя карта сохраняются, копия старых данных с метаданными остаётся в зарезервированной папке `worlds/.portable-*` для отката. Во время работы сервера миграция и файловые операции блокируются. Новый сервер обязателен: лаунчер проверяет наличие поддержки PortableWorld. Сохранение изменённых чанков сервер выполняет через 300 секунд и при штатной остановке. Полный ZIP-бэкап создаётся перед сменой версии сервера и по явной команде; обычные запуск и остановка не перепаковывают карту. Последнюю сохранённую генерацию и откат сервер обслуживает независимо от ZIP-бэкапов.

Подробности исходной публикации и сборок — в `delivery/README.md` репозитория. Поддержка старого подписанного release-feed и pinned ZIP сохранена только для совместимости и отката, в новом пользовательском потоке ссылки вводить не нужно.

## Адрес сервера

В настройках сервера есть выключенный по умолчанию параметр «Поднимать сервер через ретранслятор». При следующем запуске сервер дополнительно открывает туннель Iroh, а «Мой сервер» показывает приглашение `bscp://…` и кнопку копирования. Друг вставляет всё приглашение в обычную строку подключения; его можно сохранить в избранном. Обычный IP продолжает работать. При остановке сервера приглашение перестаёт действовать; новый запуск создаёт новое приглашение.

Iroh работает внутри того же EXE без VPN-драйвера. Backend и игровой TCP идут отдельными QUIC-потоками, UDP мира — QUIC-датаграммами с ограниченной фрагментацией и сборкой. Приглашение содержит идентификатор узла и случайный ключ доступа; передавать его следует только приглашённым игрокам. Туннель разрешает ровно три игровых направления, административные и отладочные порты не публикуются. Прямое соединение и ретрансляция выбираются Iroh автоматически. При создании приглашения лаунчер скачивает [список HTTPS-ретрансляторов](relays.json) из основной ветки репозитория. Он параллельно измеряет задержку до доступных узлов, затем подключается к самому быстрому. Если подключение к нему не удалось, пробует следующие узлы. При недоступности списка используется встроенная копия. Свой адрес можно указать в `RelayUrl` файла `config/launcher.json` — он имеет приоритет. Публичные ретрансляторы n0 бесплатны, имеют ограничения трафика и работают без гарантии доступности.

Кнопка «Синглплеер» использует уже работающий локальный сервер, вместо создания второго. При новом запуске клиент и сервер запускаются параллельно. Новый backend принимает случайный временный идентификатор запуска, зарегистрированный подписанным запросом только для этого аккаунта; перед долговременным сохранением и проверкой игровых билетов он переводится в обычную серверную сессию. HTTP-прокси ждёт готовности backend, не удерживая запуск клиентской `main`. Для старого серверного JAR без этой возможности остаётся совместимый режим: JVM запускается заранее, а вход в `main` ждёт сессию до 10 минут. Если сервер завершился при подготовке, ожидающий клиент получает ошибку и завершается.

Явная сетевая проверка без данных игроков: `cargo test -p bscp-launcher-host public_relay_carries_tcp_udp_and_revokes_invitation -- --ignored --nocapture`. Она отключает IP-транспорт Iroh с обеих сторон, проверяет TCP, UDP, крупные пакеты, неверное приглашение и освобождение локальных портов. Обычные тесты не зависят от публичных ретрансляторов.

На главной доступны избранные серверы и история последних 32 подключений. История хранится в `config/server-history.json`, сохраняет ник и объединяет одинаковые адреса с указанным и неуказанным стандартным портом. Для IP или домена без порта используется backend-порт 29545; игровые TCP/UDP-порты сообщает сервер. Явно введённый порт имеет приоритет.

В настройках нет публичного IP. Клиент передаёт адрес выбранного сервера вместе с запросом авторизации; лаунчер подписывает его вместе с остальными параметрами. Backend выдаёт TCP-адрес и адрес игрового UDP-перехода для этого подключения. Поэтому один сервер может одновременно обслуживать подключения через localhost, локальную сеть и внешний домен, без общей настройки advertised host. Bridge проверяет подпись и использует переданный адрес вместо внутреннего Host обратного прокси. Старые подписанные запросы без этого параметра используют Host запроса.

В интерфейсе показывается адрес в локальной сети. Доступ из интернета по-прежнему требует маршрутизации и открытых игровых портов; автоматическое получение внешнего IP и изменение настроек роутера не выполняются. HTTP/backend и игровые соединения должны быть доступны игроку по одному указанному имени; обычный HTTP reverse proxy сам по себе не проксирует игровой TCP/UDP.

## Диагностика и проверка

`cargo test --workspace -j 4` проверяет ядро, Supervisor и контроллер. Пример `channel_probe <root> main check|install|rollback` проверяет настоящий публичный канал без Git и токенов; команда `setup <installed-game>` подготавливает первый мир в явно указанном portable-root.

`BSCPCRAFT.exe --root <root> --rpc status|metrics` возвращает реальные данные процессов и JVM. В разделе «Багрепорт» можно описать проблему и приложить до шести скриншотов. Логи добавляются в ZIP автоматически, JFR — по отдельному выбору. Кнопка GitHub открывает заполненный issue с меткой `player-report`; ZIP нужно приложить в браузере перед публикацией.

Во время работы игры и сервера Bridge собирает исключения и метрики JVM, хост ведёт ограниченные журналы. После завершения процесса хост отправляет технические текстовые журналы сессии и накопленные события в Grafana Cloud через публичный Faro Collect URL. Скриншоты, JFR, настройки и секреты автоматически не отправляются. Очередь в `state/telemetry/outbox` сохраняется при ошибке сети; попытка доставки ограничена 12 секундами. Затем хост завершается, если больше нет игры или сервера. Параметры поставляются в `telemetry-public.json`; локальное переопределение — `config/telemetry.json`, `enabled: false` отключает отправку.

Просмотр: Grafana → Explore → `grafanacloud-vividshark1612-logs`, запрос `{service_name="BSCPCRAFT"}`. Поля `context_run_id`, `context_role`, `context_file` связывают записи с запуском и процессом. Публичный Collect URL позволяет только принимать телеметрию; приватные ключи Grafana в EXE не включаются. Проверка на отдельном профиле: `cargo run -p bscp-launcher-core --example telemetry_probe -- <qa-profile> send-synthetic`.

Ошибки лаунчера записываются в `logs/launcher-errors.jsonl` и отправляются через тот же Faro в фоне. Для поиска используйте `context_kind=launcher-error` и `context_operation=start-server`, `start-singleplayer` или `server-readiness`. В событии есть этап, код ошибки и цепочка причин. Запущенная JVM дополнительно сообщает о проблемах через журналы сессии.

Программный рендерер выбран по умолчанию. `--renderer femtovg` включает GPU. Для диагностического снимка настоящего интерфейса: `--capture <snapshot.ppm>`; окно размещается вне видимой области и закрывается после снимка, рабочий стол не управляется.

Slint Royalty-free 2.0: стандартный AboutSlint доступен через справку. Лицензии Slint, шрифта и зависимостей включаются в комплект.

## Менеджер модов

Страница «Моды» содержит каталог выбранной игровой ветки и установленные JAR. Каталог и хеши входят в подписанный `delivery.json` из `build-<ветка>`; JAR скачивается по неизменяемому Git commit, проверяется SHA-256 и описание `stalcraft-mod.properties` (API 1, ID, версия, main). Необязательные моды не входят в обязательный список игровых файлов и не устанавливаются без выбора игрока. Сейчас доступны обязательные подсказки команд, а также необязательные камера от третьего лица и кинокамера.

Установка, обновление, включение, отключение, импорт JAR и удаление работают с настоящей папкой загрузчика `profiles/default/mods` в профиле выбранной ветки. Включение хранится в существующем `enabled.properties`; обновление сохраняет выключенное состояние. Удаление перемещает JAR в `mods/archive/<uuid>` с подтверждением, настройки мода сохраняются. Для возврата можно импортировать JAR из архива. Дубликаты ID и повреждённые JAR показаны отдельно и могут быть убраны через менеджер. Обязательные компоненты нельзя отключить или удалить. Изменения запрещены, пока клиент удерживает профиль; работа отдельного сервера этому не мешает. Настройки и игровые процессы не меняются без следующего запуска.

Внешний загрузчик сейчас поддерживает клиентские моды; серверного API плагинов пока нет. Локальные JAR должны соответствовать API проекта, обычные Forge/Fabric-моды не подходят. Кнопка «Обновить список» проверяет Git и перечитывает папку; при недоступной сети остаётся сохранённый подписанный каталог.

Добавление собранного из исходников мода в каталог: запись в `delivery/mods.json` с ID, названием, описанием и папкой исходников, содержащей `src` и `stalcraft-mod.properties`. GitHub Actions компилирует необязательные модули с SDK и библиотеками текущего клиента и публикует отдельные JAR в `mods/<id>/<id>.jar`, включая их размер и хеш в подпись каталога. Исходники непроверенных модулей сами по себе не делают их доступными для установки.

Для проверки на отдельном portable-профиле: `cargo run -p bscp-launcher-core --example mod_probe -- <root> check|list|install|update|enable|disable|remove [repo:<id>|local:<hex>]` либо `import <file.jar>`.
