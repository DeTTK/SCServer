# Полная игровая сборка

## С чистого checkout

Нужны обычный Git, Python 3.10+ и JDK 17. Rust нужен для сборки EXE лаунчера, но не для игровой поставки.

```sh
git clone --branch main https://github.com/DeTTK/SCServer.git
cd SCServer
python scripts/audit_public.py
python scripts/build_player.py
```

Результат: `build/player-git/player/`. Команда не читает установленную игру, старые Releases, build-ветку или каталог разработчика. Maven-инструменты закреплены URL и SHA; сеть нужна для первой загрузки этих зависимостей. В Windows запуск клиента дополнительно использует оригинальные графические/звуковые ресурсы установленной игры, выбранной в лаунчере.

Для полной подготовки доставки, включая CAS-объекты и индексы:

```sh
python scripts/delivery.py prepare
```

`build/player-delivery/player/` — готовые файлы, `build/foundation-delivery/` — содержимое для build-ветки. Выходной каталог должен быть новым: скрипт не переиспользует загрязнённую папку прошлой сборки. Повторная сборка с новым путём: `python scripts/build_player.py --output build/player-second`.

## Что лежит в исходном Git

`bootstrap/input-manifest.json` содержит точные размер, SHA-256 и части каждого неизменяемого входа. Физические файлы находятся в `bootstrap/inputs/` и `map/data/`; файлы больше 16 МиБ разбиты на части для обычного Git, без LFS и стороннего хранилища. Сборщик проверяет каждую часть и собранный файл.

Среди входов — закрытый игровой ABI, уже приведённый к штатной JVM, оригинальные vendor-библиотеки/Windows DLL/Java 17, оригинальные `configs.xeon` и `boxes.xeon`, небольшой набор обязательных серверных метаданных и актуальная основная карта. Это необходимые зависимости игры. Собственные сервер, bootstrap, bridge, агенты совместимости, weapon-events и command-completion собираются из исходников этого checkout. Готовые сборки локалки не используются как входы.

`scripts/import_player_inputs.py` — инструмент первоначального импорта/ревизии зависимостей, а не команда CI или обычной сборки. Он не вызывается `build_player.py`. Изменение неизменяемых зависимостей требует обновления содержимого и проверяемого манифеста вместе.

## Поставка игроку

```text
Bootstrap/
  java17/
  bscp-bridge.jar
  runtime/
    game.jar
    libraries.jar
    bootstrap.jar
    imgui-compat.jar
    dependencies/
    natives/
Client/
  compat/
  mods/
Server/
  server.jar
  server.template.properties
  lib/
  fixtures/             # только реально используемые данные протокола
  registries/
  source-resources/     # небольшие закреплённые JSON, не исходники Java
  results/runtime-manifest.json
  resources/
    configs.xeon
    boxes.xeon
    overrides/
Map/
  region/
  registry.json
  object-codecs.json
  map-info.json
```

Один runtime общий для клиента и сервера. В JAR нет исследовательских `_reference-*` и временных FP-анализов. Распакованные классы, тысячные копии JSON/AABB, тестовые карты, .NET EXE, логи и пользовательские сохранения в поставку не входят.

Сервер читает оригинальные XEON через проверяемый индекс и распаковывает только запрошенную запись в память. `resources/overrides` содержит явные отличия для совместимости с закреплённым ABI; оригинальные файлы установленной игры не перезаписываются. Настройки `assets.configs`, `assets.boxes`, `assets.overrides` назначаются лаунчером автоматически. Старые loose-runtime установки ещё читаются для совместимости.

## CI и обновления

Push в `main` или `test` запускает проверки и полный рецепт сборки. После успеха CI атомарно коммитит новые CAS-объекты, индексы, дескриптор и подписанный `delivery.json` в соответствующую `build-main` или `build-test`. Подписание выполняется Actions Secret; в исходниках находится только публичный ключ.

Новая схема manifest — 2, минимальный лаунчер — 0.4.1. Старый лаунчер не должен применять новый layout. Объекты ограничены 24 МиБ, внутренние блоки — 4 МиБ; они адресуются SHA-256. Лаунчер сверяет локальные файлы, использует совпадающие данные и получает недостающие объекты. Это доставка по файлам/блокам из Git, а не скачивание полного release ZIP. Launcher EXE обновляется отдельно через Releases.

Основная карта — `merged-netdecode-20261121`. Изменение базы не подменяет уже созданные миры. Тестовые игровые профили и производственные сохранения должны оставаться отдельно от сборочных входов.
