# Инвентарь: правила клиента и серверная реализация

Разбор совместимого клиента и исправления #8, 22.11.2026. Здесь описан путь от конфига предмета до подтверждённого переноса. Игровые классы и конфиги в этот документ не скопированы.

## Что было сломано

У «Завтрака чемпиона» (`26535`) нет собственного `stack_size`. Его фабрика медицины задаёт 64 по умолчанию; склад разрешает 100000. Сервер подставлял 1. Поэтому объединение, разрешённое клиентом, откатывалось сервером. Особенно заметно это на награде из багрового ящика: `crimson_crate` выдаёт три завтрака с нативным свойством `no_drop`.

Второй сбой не связан с конкретным предметом. Массовое действие отправляет несколько обычных запросов быстрого переноса за один кадр. Сервер принимал первый, ставил инвентарю `busy` до записи и отклонял остальные. Воспроизведение: четыре стака, всего 540 патронов; клиент перенёс все четыре, сервер сохранил только первые 150.

## Из чего состоит предмет

Сетевой стек содержит ID фабрики, количество, metadata, признак состояния и его нативный двоичный блок, затем свойства. Состояние читается кодеком конкретной фабрики, а не универсальным JSON. В нём бывают UUID, износ, патроны, обвесы, содержимое контейнера и другие данные.

Свойства — отдельная нативная карта с байтовыми ключами и типизированными значениями. Это не только картинка предмета или его имя. У двух одинаково выглядящих завтраков могут различаться `no_drop`, персональность, срок действия или другие свойства.

Правила сохранности:

- перенос меняет адрес, а не создаёт предмет заново;
- количество при разделении сохраняется;
- UUID, metadata, состояние, свойства и нативная геометрия остаются у исходного предмета;
- разные состояния и свойства не объединяются ради внешне одинакового значка;
- выдача нового экземпляра и редактирование существующего — разные операции;
- точное состояние в журнале остаётся источником истины, клиент не присылает новый стек вместо переносимого.

У девяти изученных фабрик количество может быть больше единицы и при наличии состояния. Их нативное сравнение включает базовые UUID/привязку и поля конкретного состояния. Объявлять все такие предметы одинаковыми или вырезать UUID ради стака нельзя.

## Адреса и геометрия

| Область | Серверный адрес | Что означает |
|---|---|---|
| Экипировка | aggregate 0, container — слот, slot 0 | Отдельные корневые слоты. Совместимость выбирает штатный интерфейс; сервер проверяет структуру и количество |
| Рюкзак | aggregate 1, container 0 | Сетка 8×20, 160 ячеек |
| Персональный склад | aggregate 2, container — страница | 15 страниц. Обычно 800 ячеек; страница 12 — 8000 ячеек и без внесения предметов |

В окне склада клиент показывает его как локальный aggregate 0/container 0, owner -1. `InventoryPackets` переводит этот адрес в серверный aggregate 2 и текущую страницу. Owner 0 относится к инвентарю персонажа. Нельзя смешивать owner со страницей или использовать его как ID персонажа.

Корень предмета занимает прямоугольник. Покрытая им ячейка не является ещё одним предметом. Размеры `slot_size` округляются вверх, учитывается наследование объекта. У оружия размер может меняться из-за обвесов; его фактический размер вычисляет нативный адаптер и сохраняет в `nativeGridWidth`/`nativeGridHeight`. На сетевой формат самого предмета эти поля не влияют.

## Как конфиги влияют на инвентарь

| Данные | Результат |
|---|---|
| `type` | Выбирает фабрику и её правила по умолчанию; влияет на состояние, действия и сортировку |
| `stack_size` | Лимит обычного семейства предметов, если его фабрика читает это поле |
| `stacksize` | Лимит именно `game_object`. Не заменяется одноимённым по смыслу `stack_size` |
| `extends_gameobject` | Наследование свойств объекта, в том числе `stacksize` и размера. Цикл/слишком длинная цепочка отклоняются |
| `slot_size` | Прямоугольник в сетке с нативным округлением вверх |
| Обвесы внутри состояния | Могут изменить фактический прямоугольник оружия |
| `weight`, бонусы веса | Вес и грузоподъёмность; разрешение стака не делает предмет невесомым |
| `bind_state`, свойства персональности | Ограничения передачи/выбрасывания и различие стаков |
| `can_drop_manually`, `no_drop` | Правила выбрасывания, а не вместимость стака |
| Срок действия и прочие свойства | Сохраняются вместе с предметом и могут мешать объединению |
| Типизированные `tag` награды | Применяются через нативный NBT/кодек. Не удаляются при выдаче, сортировке или переносе |
| Конфиги медицины, оружия и брони | Задают действие предмета, расчёт характеристик и состояние; перенос не подменяет их тип или содержимое |

Разрешение объединить два предмета и количество, помещающееся в ячейку, — разные проверки. Лимит склада также не заменяет лимит рюкзака. В изученном клиенте предметы с обычным лимитом больше 1 получают складской лимит 100000; настоящие одиночные предметы остаются одиночными.

### Отсутствующее поле не означает один предмет

`NativeStackRules` содержит проверенные значения конструкторов. Например:

| Семейство | Лимит без собственного поля |
|---|---:|
| Медицина и еда | 64 |
| `game_object` | 64, с учётом собственного/унаследованного `stacksize` |
| Обычные custom-предметы, ящики, облики, часть жетонов и квестовых вещей | 100 |
| Гранаты | 60 |
| Ядра модулей и средства снятия | 99 |
| Жетоны репутации | 100000 |
| Образцы frontline/dmz2026 | 1000 |
| Новогодний player_grant | 10000 |

Собственные значения конфигов сохраняют приоритет там, где их действительно читает нативная фабрика. Старый частичный `native-resource-stack-defaults.json` не отключает новые проверенные семейства. При добавлении нового типа нельзя назначать всем неизвестным предметам 64 или 100000: оружие, броня и уникальные состояния должны оставаться защищёнными.

Есть отдельная нативная фабрика квестового предмета `16999`: она задаёт одиночный стек вопреки общему `stack_size: 5` в ресурсе. Это явно описанное исключение, а не общее правило для всей квестовой категории.

## Какие действия отправляет клиент

Штатные кнопки сохранены:

- Shift + ЛКМ — быстрый перенос выбранного стака;
- Ctrl + Shift + ЛКМ — перенос предметов этой фабрики; штатный обработчик рассматривает до 50 корней за действие;
- Shift + ПКМ у еды и медицины — использование предмета.

| ID запроса | Назначение |
|---:|---|
| 1231 | Обычный перенос/обмен двух адресов |
| 102 | Перенос заданной части стака |
| 1627 | Вариант с nullable-адресом и owner в конце |
| 2040 | Вариант разделения с owner в конце |
| 2009 | Быстрый перенос: source, целевая область, фактически изменённые адреса и запрошенное количество |
| 1506 | Сортировка рюкзака или открытой страницы склада |
| 523 | Контекстное «Удалить»: owner, sequence и точный адрес корня |

Нативные классы: стек `211097523`, фабрика `1366800141`, агрегат `47325642`, контейнер `830050478`, сетка `175688206`, менеджер `105205961`, окно `1984657417`/`833813734`, быстрый пакет `796253964`. Числа относятся к проверенному ABI; в другой версии клиента их надо сверять заново.

Менеджер клиента сначала рассчитывает результат локально и блокирует затронутые адреса до ответа. Сервер отправляет изменения или снимок, затем ACK с исходными owner/sequence. Нельзя подтвердить ещё не записанный результат. При полном рюкзаке клиент может отправить 2009 с пустым набором изменённых адресов: это отсутствие переноса, требующее ACK, а не испорченный пакет.

## Как работает сервер после исправления

`InventoryTransferQueue` хранит FIFO отдельно для каждой сессии. Повтор уже ожидающей пары owner/sequence не исполняется ещё раз. Активные задачи входят в бюджет: до 256 запросов/512 КиБ на сессию, до 2048/8 МиБ суммарно. Ушедшая сессия освобождает очередь; уже принятая запись журнала завершается штатно.

После освобождения инвентаря берётся до 64 запросов. Их планы последовательно считаются на рабочем потоке относительно одной неизменяемой исходной ревизии. В журнал попадает один конечный delta и одна новая ревизия. Если расчёт не проходит, этот пакет не публикуется частично; зависимый хвост отменяется, клиент получает действительный снимок и ответы.

Перед запуском проверяются доступность персонажа, owner, страница склада и срок ожидания. После записи проверяется, существует ли ещё исходная сессия. Небольшие изменения идут точечно; большие перестановки без экипировки — снимком. Изменения экипировки проходят прежнюю нативную подготовку внешности, оружия и характеристик. Обычные действия не обходят проверку количества, занятых ячеек и журнала.

Это исправление серверное: сочетания клавиш, клиентский UI и расчёт клиентского переноса не заменяются.

## Удаление и корзина

Контекстное действие «Удалить» (`delete_item`) отправляет пакет `523` (класс `749436561`): owner, sequence, затем один точный адрес корня без nullable-маркера. Поля owner/sequence подставляет общий слой отправки клиента, как и у кнопки открытия ящиков.

Диалог клиента перед удалением показывает срок восстановления `7` дней (`Duration.ofDays(7)`) и строки `stalker.ui.context_menu_action.sure.delete.*`. Сам интерфейс корзины описан ключами `stalker.inv_view.trash_storage.*`, `darken_trashed_items` и `trashedItems`. Это клиентская часть «корзины»: серверу она не передаёт удалённый предмет.

Сервер принимает `523` и атомарно удаляет корень по адресу: рюкзак и экипировка при owner `0`, открытая страница склада при owner `-1` (локальный адрес склада нормализуется в aggregate `2` и текущую страницу). Полное удаление убирает корень, частичное — уменьшает количество; частичное удаление используется существующей чат-командой. Ответ — ACK с исходными owner/sequence и точечное изменение или снимок.

Ограничение: серверной корзины с семидневным хранением и восстановлением пока нет. Предмет удаляется безвозвратно, хотя клиентский диалог обещает восстановление. Для полной совместимости нужны отдельное хранилище удалённых предметов, срок хранения и запрос восстановления; клиентские строки и подтверждение уже готовы к такому сценарию.

## Старые сохранения

Правила отмечаются политикой `native-inventory-rules-v3`. Сканирование и перенос проходят до открытия игровых портов. Увеличившийся лимит не заставляет автоматически переиздавать предметы: старые одиночные завтраки просто можно объединить.

Для ранее ошибочно выданного стака предмета `16999` применяется отдельное восстановление количества. Первый экземпляр сохраняет исходный UUID, посчитанные дополнительные экземпляры получают новые UUID через нативный кодек. Количество, metadata и остальные данные сохраняются; свободные позиции подбираются штатным repack. Проверен повтор после прерывания перед публикацией маркера: новые копии не создаются второй раз.

Ни `characters.sjournal`, ни персонажей для обновления удалять не нужно. CRC-повреждения и действующая блокировка другим сервером не игнорируются.

## Что проверено и где границы проверки

Из работающего совместимого клиента сняты правила 8783 фабрик. Общая часть с серверным каталогом содержит 8745 ID. До исправления в ней было 225 расхождений лимитов; после — ноль для рюкзака и склада. Несовпадение состава каталогов — отдельный результат: 38 фабрик есть только в выбранном клиентском профиле, 43 определения — только в серверном. Эти элементы не объявлены проверенными совпадениями и не заменены догадками о моделях/кодеках.

Проверены конструкторные значения, обе формы имени поля стака, наследование, состояние и свойства, пять форм запросов по декодерам, массовый обработчик клиента, очередь и запись. Реальные прогоны включают завтраки, тег `no_drop` как в багровом ящике, обычные/персональные варианты, патроны, 159 уникальных детекторов, полный рюкзак, частичный перенос и повторный вход. Устойчивость сетки проверяется по корням и всем покрытым ячейкам.

Это не обещание реализации каждой торговой, квестовой или боевой системы: они используют предметы, но не сводятся к инвентарному переносу. В этой работе их неподключённые сценарии не заменялись выдуманными правилами.

Проверки без игровых файлов:

```sh
python scripts/build.py test
```

В набор входят `NativeStackRulesTests`, `InventoryTransferQueueTests`, сортировка, удаление корня (`InventoryDeleteTests`), восстановление карты/инвентаря и журнал. Нативные сопоставления и игровые прогоны отражены в `validation-inventory-contract-20261122.json`.
